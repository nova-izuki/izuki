# Working together on Izuki (Claude + ChatGPT/Codex + Freebuff)

Three AI assistants work in this repo for the same owner, sometimes at the
same time. The full rules are in [AGENTS.md](../AGENTS.md). Read this before editing, and update it when you take or finish
something. Small, atomic edits only: never rewrite a whole file another
assistant is also changing.

## Ground rules (from the owner)
- Work on the milestone branch (`milestone-196`, draft PR #16), never
  straight on `main`: a version bump on `main` publishes by itself, and every
  push there redeploys the website. Before pushing, run `./tools/test-windows.ps1`
  (the Windows Rust tests: it sets `IZUKI_TEST_MANIFEST=1`, which plain
  `cargo test --lib` does not — without it the test binary loads Common
  Controls v5 and dies with `STATUS_ENTRYPOINT_NOT_FOUND` before the harness),
  `npx tsc --noEmit`, `npm run build` and the `test:*` scripts for what you
  changed. CI (`verify.yml`) runs the full set on every push to the branch.
- **Standing release authorization (owner, 2026-11-03, restated):** verified
  work is pushed, merged, released, deployed and delivered as an update
  without asking the owner each time (AGENTS.md rule 2). Every earlier rule
  here requiring the owner's approval to merge or publish is superseded.
  Claude coordinates merges and releases so nothing is published twice;
  Freebuff and Codex push verified work and mark it ready here.
- CodeRabbit reviews each push to the PR. Before fixing a finding, claim it
  in `docs/REVIEW-1.0.196.md`, then follow "Code review" in AGENTS.md.
- Approved exception for 1.0.163: on October 24, 2026, the owner explicitly asked Codex to release this tested batch through the updater. Codex owns this release only.
- **Only Claude bumps the version and releases.** Codex and Freebuff push
  without touching versions, then add a line to `docs/NEXT-RELEASE.md`.
  Claude ships it with the next release.
- Never commit the owner's personal face model, keys, emails or phone numbers.
- Nothing is sent, posted, deleted or bought without the user's explicit yes.
- Never claim something works without testing it; say what wasn't verified.

## Enter in a message box was an unguarded send (Freebuff, 2026-11-27, follow-up)

## Injected code cannot see module scope (Freebuff, 2026-11-27, owner report)

The owner found the page actions dead in the real browser: with the switch on,
the panel read a page and got no controls at all. `chrome.scripting.executeScript({
func })` does not send a function and its neighbours — it sends `func.toString()`
and runs that in the page, where nothing from the module exists. The Enter guard
had left `sendsFromHere` at module scope and `pageControls` called it by name, so
the page ran a call to a name it did not have, threw `ReferenceError`, and the
panel received `null`. Every check passed, because they import the module, where
the name resolves: the suite was testing the same code the way the panel calls it,
not the way Chrome runs it.

`sendsFromHere` is now a `const` arrow inside `pageControls`, so it is part of the
serialised text; the comment above it says why, and `pageControls` keeps its literal
120/60 limits for the same reason (`MAX_ITEMS` and `actionTags` are module scope).

New case, “every injected function runs from its own text, with no module scope”:
on the stub DOM it runs `new Function('return (' + fn.toString() + ')')()` for
`pageControls`, `clickControl` and `typeControl` and never the imported function, so
any module reference throws the same `ReferenceError` Chrome throws; it also checks
the Enter mark, a click and a refused Enter from that bare copy. Proven both ways:
rebuilding the shipped shape on a copy makes that one case fail with
`ReferenceError: sendsFromHere is not defined` while the other 11 pass; the fixed
file passes 12 of 12 in `npm run test:panel`, with `node --check` and
`git diff --check` clean. Not proven: that the injected code behaves the same in a
real page — only that it carries everything it calls.

## Chat boxes are fields too (Freebuff, 2026-11-27, owner request)

## A task runs to the end, and a composer's Enter is a send by default (Freebuff, 2026-11-27)

Two things the owner asked for after using the page actions.

**Enter in a composer.** Marking only the boxes whose name said "message" left a hole:
a chat box called "Write something", or a page that names none of them, still sent on
Enter. An editable box (contenteditable or `role="textbox"`) now sends by default, and
only a box that names itself long-form keeps its Enter — body, compose, editor,
document, draft, note, description, article — because in Gmail's body Enter is a new
line and Send is a separate button. The check happens before the Send button search, so
Gmail's own Send button cannot re-mark its body. Textareas are unchanged.

**The loop.** `ask()` used to do one answer's tags, take one look at the page and stop.
It now carries the task through: `actTask()` spends what is left of a budget
(`MAX_STEPS = 12`, `MAX_ROUNDS = 5`, both in `page-actions.js` with `moreRounds()`),
each round re-reads the page and the numbered controls, and after every round `ask()` is
called again with what was just done instead of the question. It stops when an answer
carries no tags, when the budget is gone (and says so: "That's 12 steps in one go — say
"keep going""), when another question is waiting, or when the person presses Stop — the
epoch counter that guards every request covers the loop too. The prompt tells the model
it may take up to twelve steps and should answer in words when nothing is left.

Three things the loop would have made worse, fixed with it: the question is no longer
written into the history again on every round (only the first round adds it, later rounds
add what was done); a tag is never read aloud by read-aloud; and tags are stripped before
an answer is saved to recent chats. A round whose answer is only tags shows no answer
bubble — the step lines already say what happened.

Checked here: 15 cases in `tools/panel-actions-check.mjs`, the new ones being a chat box
named "Write something" (numbered, `sends: true`, Enter dropped) beside Gmail's
"Message Body" with a Send button next to it (`sends: false`, Enter fires), and the budget
rule at its edges (`moreRounds(8, 2)` true, `moreRounds(12, 3)` false). `npm run
test:panel`, `node --check` on the panel and `git diff --check` pass. Not checked: the loop
itself has never run — it lives in `sidepanel.js`, which no test drives, so the
continuation, the stop mid-task and the budget message have only been read, not seen.
**The hand-off the loop died on.** `ask()` began with
`if (!question || busy || starting || desktopTask || !current) return false`, so every
question — including a task's own next round — was refused while the panel was busy. The
loop schedules that next round 20 ms after it finishes, and `askNext()` (or a Send) can
make the panel busy inside those 20 ms, so the continuation hit `busy`, returned `false`,
and the task ended with no divider, no error and nothing in the chat to say why. The guard
is now `startNow()` in `page-actions.js`, which answers `start`, `refuse` (a question the
person typed; the panel queues it, exactly as before) or `wait` (a continuation). A waiter
polls ten times a second for up to six seconds, then says it stood back and could not pick
the task up again; if the epoch moved it returns at once, so Stop and Clear still end it.
The task object now carries `epoch` for that (`{ steps, rounds, epoch }`), which is why
`const task = walk || …` moved above the guard.

**A round that changes nothing.** `actTask()` returned only its sentence, which is non-empty
even when every step failed ("Couldn't press item 5"), so a page that renumbered the control
away was asked again until the round budget ran out. It now returns `{ text, count }` and
`ask()` keeps `landed`; `roundVerdict()` in `page-actions.js` decides `quiet` (no tags),
`queued` (a question waiting), `unchanged` (tags, but the page took none — the task stops
with "That's where it stopped — nothing on the page changed"), `budget`, or `again`.
`moreRounds(steps, rounds, landed)` also requires `landed > 0`. A press the page accepts but
does nothing with still counts as taken: the panel cannot see intent, only that the element
was there and the browser ran it.

**Driven for real: `tools/panel-loop-check.mjs`** (added to `npm run test:panel`, eight
checks). It drives the rules across rounds against a stand-in page: a three-step form takes
three rounds and stops because the answer asked for nothing, not because it ran out; a round
the page takes nothing from ends the task; the budget ends it by steps (twelve, in three
rounds of four) and by rounds (five, of one); a waiting question ends it with no round spent;
Stop ends it after the round it lands in. Then it checks the guard directly (`startNow()`:
`wait` for a continuation, `refuse` for a typed question) and reads `sidepanel.js` to prove
`ask()` calls both rules, keeps `landed`, hands the same task to the next round, and no longer
calls `moreRounds()` itself. What it does not do is run `ask()`: the panel needs
`chrome.scripting` and a live tab, so the rules are what is driven here, not the panel. A real
two-round task in Chrome is still unrun.

**A page to try it on: `tools/fixtures/page-actions.html`** (CRLF, one file, nothing fetched).
A message box labelled "Message" with a Send button (the panel types, drops the Enter, and
never presses Send because of its name); a long-form "Message body" with a Send button (there
Enter is a new line, so the panel may press it); a three-step form whose steps hide each other,
so the numbers move and each round has to read the page again; a password box that must never
be numbered; and "Press me once", which removes itself so asking a second time is the step
that changed nothing. Everything it sees is written into a log at the bottom, so a manual run
reads as a list rather than a guess. To use it: `chrome://extensions` → Izuki → Details →
"Allow access to file URLs" (`chrome.scripting` cannot reach a `file://` tab without it), open
the file, then turn on "Let Izuki use this page" and "Share this tab" in the panel and ask
"fill in the three-step form" or "write hello into the message box".
